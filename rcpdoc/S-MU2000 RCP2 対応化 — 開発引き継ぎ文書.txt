## 3. これまでに実装した機能

### RCP2 の解析基盤

- 固定ヘッダー、トラックヘッダー、4-byte シーケンスレコードの解析。
- FE（Track End）までのシーケンス解析。
- 未知コマンドを生データとして保持する中間表現。
- F6/F7 コメントデータの抽出。
- トラック識別を維持した複数トラックの tick 順統合。

### 時間展開と移調

- ノート、F5 key signature、E7 tempo の時間展開。
- EB Control Change、EC 標準 Program Change、EE Pitch Bend の部分対応。
- 符号付きトラック開始オフセットの適用。
- 負の tick は 0 にクランプし、32-bit 範囲超過はエラーにする。
- ValleyBell の参照実装に合わせたトラック移調・文書移調・リズムチャンネル判定・7-bit ノート折返し。
- ノート duration から note-off を生成する文書レベルの時間展開。

### ノート gate / note-off の仕様

現在の実装では、次の挙動を扱う。

1. duration=0 のノートは発音イベントとして出さない。
2. duration が正なら開始 tick + duration に note-off を配置する。
3. 同一トラック内で同じ移調後音高が既に鳴っている場合、新しい note-on を追加せず、既存 note-off の tick を更新する。
4. note-off は対応するノートの移調後音高を引き継ぎ、内部表現では velocity=0 とする。
5. gate 展開後に符号付き開始オフセットを適用するため、note-on と note-off の両方に同じオフセット規則が適用される。

参照資料：

- [ValleyBell/MidiConverters — rcp2mid.c](https://github.com/ValleyBell/MidiConverters/blob/master/rcp2mid.c)

### EB / EC / EE の制約

- EB：p1 を controller、p2 を value として扱う。データは 7-bit 範囲内。
- EC：p1 が `0x80` 未満の場合のみ標準 Program Change として扱う。
- EC の `0x80` 以上は特殊インストゥルメント処理として明示的に拒否する。
- EE：p1/p2 を 7-bit データとして保持する。
- MIDI status byte への変換や実際の出力層への接続は未実装。

## 6. 次に進める作業

### 優先 1：実際の MIDI 出力経路を調べる

`src/rcp.h`、`src/rcp.cpp` の内部表現を確認し、既存の MIDI 出力・イベント送信・ファイル読込経路を調査する。

まず確認すること：

- 既存の MIDI イベント表現はどこにあるか。
- ノートオン・ノートオフをどの層で生成しているか。
- SMF の読み込みや出力と、音源へのイベント送信がどう接続されているか。
- 新しい `rcp::timed_event` を既存経路に接続できるか。
- チャンネル番号と同 tick のイベント順序をどこで決めるか。

既存実装に合わせて設計し、RCP2 専用の出力経路を無理に独立させない。ファイル名や API を推測せず、最新ブランチのコードを確認する。

### 優先 2：接続に必要な最小変換を実装する

既存経路を確認した後、必要な範囲に絞って以下を実装する。

- ノートオンとノートオフの変換
- MIDI チャンネル番号の付与
- EB / EC / EE のイベント変換
- tick とイベント順序の維持
- 未対応イベントの明示的なエラー処理

実装と同時に `src/verify.cpp` と `tests/verify.txt` を更新し、CI を実行する。

### 優先 3：実データで比較する

合成テストに合格したら、使用許可のある小さな RCP2 サンプルを使い、参照コンバーターの出力と比較する。テスト用データの出所、期待結果、実行環境を記録する。

`/r/roms` はアップロードしない。

## 7. 開発手順

1. GitHub から最新の `feature/rcp2-parser-skeleton` の SHA と対象ファイルを取得。
2. `rcpdoc/NEXT_STEPS.md` と `rcpdoc/CHECKLIST.md` を確認。
3. 既存の MIDI 出力経路を調査。
4. 小さい単位で実装し、回帰テストと baseline を更新。
5. 必要に応じて `FACTS.md` と `LOG.md` を更新。
6. feature ブランチにコミット。
7. GitHub Actions の最新 run を確認し、すべての必要なジョブの結論が `success` になるまで完了扱いにしない。
8. 失敗した場合はログを取得して原因を修正し、再実行結果を確認する。
