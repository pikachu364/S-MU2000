# RCP2 対応設計メモ（ドラフト）

**状態:** 実装初期段階（固定ヘッダー、トラック走査、未解釈シーケンス解析）  
**対象:** S-MU2000 での RCP2（`.rcp`）解析・再生  
**目的:** 実装の分担、既存コードとの接続、未確定事項を整理する。

## 現在の実装状況

- `src/rcp.h` / `src/rcp.cpp` で RCP2 の識別文字列、固定ヘッダー（0x586 bytes）、トラックヘッダー（0x2c bytes）を読み取る。固定ヘッダーからタイトル、コメント、TPQ、テンポ、拍子、キー、PlayBIAS の生バイト、トラック数を取得し、トラックヘッダーから長さフィールド、ID、リズム設定、MIDIチャンネル、キー値、tick offset、ミュート、名前を取得する。
- `parse_tracks` が固定ヘッダーのトラック数に従ってトラックを走査し、トラック長の下限・ファイル末尾境界・各トラック内の FE 終端を検証する。長さフィールドは参照資料に従い、長さフィールド自身を含む全トラック長として扱う。
- `build_intermediate` が文書ヘッダー、トラックヘッダー、未解釈の 4 byte レコードを中間表現にまとめる。各レコードのトラック内インデックスと生パラメーターを保持し、tick やコマンド意味論は推測しない。失敗時は出力を空にする。
- 4 byte のシーケンスレコードを生データのまま読み、FE (Track End) までを返す `parse_sequence` を追加した。コマンドの展開・時間解釈は行わず、終端なし・途中で切れた入力は拒否する。
- `decode_note_event` がノートレコード（code 0x00〜0x7F）を note / delay / duration / velocity に分ける。コマンド（0x80〜0xFF）はノートとして扱わず拒否する。delay の絶対 tick への変換、duration の時間解釈、移調・テンポ適用はまだ行わず、元の生レコードは中間表現に保持する。
- ノート解釈テストでは通常値に加えて、ノート番号の上端 0x7F、コマンド境界 0x80 / 0xFF、成功時のエラー文字列クリア（初回およびコマンド拒否後）を確認する。境界の値は合成データで検証し、時間計算の仕様とは分離している。
- `verify` に合成したヘッダー／トラックヘッダー／シーケンスレコードのテストを追加した。実データや商用曲は含めない。
- Makefile と CMake の共通コアに登録した。
- **MIDI への変換・再生は未実装。** この段階では RCP2 の曲を再生できない。イベントの時間計算、特殊コマンドの意味、トラック終端後の余剰バイトの意味は未確定。
- ヘッダーの項目位置は [ValleyBell/MidiConverters の RCPFormat.txt](https://github.com/ValleyBell/MidiConverters/blob/master/RCPFormat.txt) の表を参照。これは第三者による解析資料であり、公式仕様として断定しない。
- 識別文字列は既存コンバーターの判定を参考にした。ヘッダー全体のレイアウトやイベント仕様は、実ファイルと複数実装の照合後に確定する。


> この文書は設計案であり、RCP2 の正式仕様や実機との完全な互換性を示すものではない。既存実装で確認した挙動と、形式全体で確定した仕様を区別する。

## 1. 対象範囲

初期実装では RCP2（`.rcp`）を対象とする。RCP3（G36/R36）は将来の拡張候補とし、CM6/GSD は初期対象外とする。

既存プレイヤーやコンバーターは、ファイル形式と変換結果を調べるための参考資料として扱う。特定実装で確認できたヘッダー長、イベント形式、コマンドの意味などを、そのまま全 RCP2 ファイルに共通する正式仕様とみなさない。

## 2. 推奨する処理構成

処理を次の段階に分ける。

1. **ファイル解析:** ヘッダー、トラック情報、イベント列を読み取る。
2. **中間表現:** トラック、イベント種別、パラメーター、相対位置などを保持する。
3. **イベント展開:** テンポ、ループ、小節リピート、継続データなどを処理する。
4. **時間変換:** 展開後のイベントを時間情報付き MIDI イベント列へ変換する。
5. **再生側への引き渡し:** GUI、VST3、オフラインレンダーなど、それぞれの実行環境に適した方法でイベントを処理する。

ファイル解析・イベント展開と、S-MU2000 固有の MIDI／SysEx 配送は分離する。これにより、RCP の解釈と、音源側での再現性を別々に検証できる。

### 時間フィールドに関する比較調査（未確定）

第三者実装を比較した範囲では、次の共通点と注意点が見つかった。

- RCP2 の 4 byte レコードについて、ValleyBell/MidiConverters の `rcp2mid.c` は先頭 byte をノート番号またはコマンド、2 byte 目を delay、3 byte 目を duration、4 byte 目を velocity として読み取る。ノートの発生位置は、そのレコードを処理する時点のトラック時刻で、duration はノート終了時刻の計算に使われている。
- 同実装では duration が 0 のノートは出力しない。また、同じ高さのノートが既に鳴っている場合は、終了時刻を更新する処理がある。
- Gearmulator の `RcpFilePlayer.cpp` も、ノートを現在 tick に置き、duration から終了 tick を求め、通常のノートや一部コマンドの後で delay を時刻に加算している。
- ただし delay の扱いは全コマンドで一律ではない。Gearmulator では高いコマンド番号の一部を時間を進めないコマンドとして扱い、ループ終端の delay を反復回数として読む例もある。ValleyBell 側でも、コマンドによって delay フィールドを別の用途に使ったり、時刻加算を抑制したりする処理がある。

参照:
- [ValleyBell/MidiConverters: rcp2mid.c](https://github.com/ValleyBell/MidiConverters/blob/master/rcp2mid.c) — RCP2 のレコード読み取り、ノート長、コマンド別 delay 処理。
- [Gearmulator: RcpFilePlayer.cpp](https://github.com/masanaohayashi/gearmulator/blob/codex/pr-rcp-player/source/ronaldo/88emu/88emuplayer/RcpFilePlayer.cpp) — 現在 tick、ノート終了 tick、コマンド別の時刻進行。

**この比較だけで正式仕様が確定したわけではない。** 実装間でコマンドの対応や例外処理が異なる可能性があるため、現段階では時刻展開コードを追加しない。特に「delay は必ず全イベントの後に加算する」と一般化せず、コマンド分類・パラメーター用途・時刻進行を分けて設計する。今後は各コマンドの表と合成テストを用意し、仕様が確認できたものから実装する。


### コマンド棚卸し（第三者実装ベース・暫定）

下表は ValleyBell の `rcp2mid.c` にあるハンドラー名を整理したもの。**正式仕様の確定表ではなく、当該コンバーターがどう解釈しているかの調査インデックス**として使う。パラメーターの詳細・例外条件・対応機種は、実装箇所と実データを照合するまで確定扱いにしない。

| コード範囲／値 | 参照実装での用途 | 時刻・パラメーターについての注意 |
|---|---|---|
| `0x00–0x7F` | ノート | 先頭 byte がノート番号。2 byte 目を delay、3 byte 目を duration、4 byte 目を velocity として扱う。ノートは処理時点の tick に置かれ、duration 0 は出力しない。 |
| `0x90–0x98` | ユーザー定義 SysEx、直接 SysEx | 参照実装はヘッダー内テンプレートや後続継続レコードを参照する。SysEx のデータ構築と delay の扱いは別々に検証する。 |
| `0xC0–0xCF`（一部） | Yamaha 系などの機種固有パラメーター／機能 | 各値が同じ形式を共有するとは限らない。C4 など、ハンドラー一覧に現れない値も含め、未確認コードを類推で補わない。 |
| `0xD0–0xDF`（一部） | Yamaha XG／Roland 系のアドレス、データ、パラメーター、機種指定など | 複数レコード間で値を組み立てるコマンドがある。単独レコードだけで意味を決めない。 |
| `0xE1–0xE2` | XG／GS 楽器設定 | 出力先・チャンネル等の条件を含めて確認が必要。 |
| `0xE5–0xE7` | Key Scan、MIDI チャンネル、Tempo Modifier | E7 は参照実装で tempo modifier として処理される。値をそのまま BPM やミリ秒と解釈しない。 |
| `0xEA–0xEE` | チャンネル・コントロール、楽器、アフタータッチ、ピッチベンド等 | 参照実装では MIDI チャンネルや出力先を見て処理する。データ値と時間フィールドを混同しない。 |
| `0xF5` | Key Signature Change | ValleyBell 実装では delay byte をキー値として使い、通常の時刻加算を抑制する。 |
| `0xF6` | コメント | 追加テキストを読む特殊処理。delay byte を通常の待ち時間として扱わない。 |
| `0xF7` | 継続レコード | 先行コマンドの継続データとして参照される場合がある。単独イベントとしての扱いは文脈依存。 |
| `0xF8–0xF9` | ループ終端／開始 | F8 の delay byte がループ回数として使われる実装例がある。ループの時刻展開は通常イベントの delay 加算とは分ける。 |
| `0xFC–0xFD` | 小節リピート／小節終端 | 小節位置やリピート状態を更新する処理がある。ループ展開の状態機械として検証する。 |
| `0xFE` | トラック終端 | 参照実装ではトラック処理を終了し、delay を 0 にする。現パーサーはこれをシーケンス終端として扱う。 |
| その他／未掲載値 | 未調査、または当該実装で専用ハンドラーが確認できない | 未知値の意味を近いコードから推測しない。安全な拒否・保持の方針を別途決める。 |

この表はハンドラーの存在と大まかな用途を列挙しただけで、全コードの網羅性や他の RCP2 実装との一致を保証しない。特に `0xF0–0xFF` 全体を「時間が進まない」と一括りにするのは不正確であり、個々のコマンドごとに状態変更・データ消費・時刻進行を記録する。

次にコードを実装する前に、各コマンドについて少なくとも次の列を埋める: **コード、パラメーター用途、後続レコード消費、時刻進行、状態変更、参照元、合成テスト**。未確認セルは「未確定」とし、推測で補完しない。

## 4. S-MU2000 への接続で注意する点

S-MU2000 には MIDI イベントを処理する既存経路があるが、フロントエンドによってタイミング管理とイベントの受け渡し方が異なる。

- VST3 側にはサンプル位置付きイベントを処理する経路がある。
- GUI 側の MIDI 入力経路は、MIDI バイト列を音源へ渡す処理を含む。
- `render.exe` にはオフラインで MIDI を処理する経路がある。
- バイト列キューを、サンプル位置付きイベントのスケジューラーと同一視しない。

共通処理が生成するイベントの時間表現を決めたうえで、各フロントエンドへの配送方法を個別に設計する。ブロック境界、同時刻イベントの順序、既存入力との競合、再生停止・再開時の状態は確認が必要である。

## 5. テスト方針

第三者の楽曲ファイルをリポジトリに保存せず、テストコードで小さな合成バイト列を生成する。

推奨する順序:

1. 最小ヘッダーと空トラック
2. 1 音のノートオン／ノートオフ
3. step と gate によるイベント時刻
4. テンポ変更
5. ループと小節リピート
6. ユーザー SysEx と継続データ
7. 不正・途中で切れた入力
8. 既存コンバーターとの出力比較

各テストでは、入力バイト列、期待するイベント列、実際のイベント列を分けて記録する。イベント内容と時刻の検証を、音源から出る音の一致とは別に扱う。

既存テスト方針も参照する: [S-MU2000 回帰試験](https://github.com/tarboh/S-MU2000/blob/main/doc/testing.md)。

## 6. 未解決事項

次の項目は、確認できるまでは確定仕様として扱わない。

- ループの入れ子、終了条件、特殊値
- SameMeasure（同小節参照）の意味と展開順序
- 相対テンポやテンポ変化の時間計算
- ユーザー SysEx の特殊値、チャンネル挿入、チェックサム
- MIDI ポートとトラックの対応
- 同時刻に発生するイベントの順序
- 未知コマンドや不正入力の扱い
- GUI、VST3、オフラインレンダー間のタイミング整合性

観察結果には、可能な限り再現手順、参照した実装・ファイルの種類、確信度を添える。実ファイルや既存コンバーターの結果と矛盾する場合は、差分を記録してから仕様判断を行う。

## 7. データと公開範囲

テストには合成データを優先し、商用・第三者の楽曲ファイル、ROM、ファームウェアなど公開に適さないデータを追加しない。調査途中の推測は確定事項として記述せず、未解決事項として残す。
